# Security policy

## Reporting a vulnerability

Please report security issues privately through GitHub's "Report a vulnerability" button on the repository's Security tab (private vulnerability reporting). Do not open a public issue.

You will get an acknowledgement within 72 hours and a fix or mitigation plan within 14 days for confirmed issues.

## Scope

This package handles private keys, so nearly all of it is security-relevant. Reports about any of the following are especially welcome:

- **Server verification.** `createAgent` sets `rejectUnauthorized: true` unless `dangerouslyDisableServerVerification` is passed explicitly, and warns through `onWarning` every time it is. On a mutual-TLS connection, disabling verification means presenting the client certificate to whatever host answered; the supported fix for an unverifiable server is `caPem`. A path that reaches an unverified agent without that option being set is a vulnerability.
- **Key exposure.** The private key exists only in memory, is never written to disk by this package, and appears in no `toString`, `toJSON`, log line or CLI output. Certificates are identified by a SHA-256 fingerprint instead. Anything that causes key material to be printed, serialised or persisted is a vulnerability.
- **Identity mix-ups.** `AgentCache` is keyed on the certificate's fingerprint specifically so that a service holding one certificate per customer cannot serve one customer's identity on another's request. A way to get the wrong agent out of the cache is a vulnerability.
- **Parsing.** The package parses attacker-influenced bytes when a certificate comes from an upload or an external store. Crashes, unbounded memory use or anything worse in `readPkcs12` are in scope.

## Not in scope

Every certificate in this repository is generated by `npm run fixtures`: self-signed, synthetic, organisation "Example Organisation" in country `ZZ`, with a throwaway key created seconds before. They are test data, and their private keys are published on purpose. Reporting them as leaked keys is not needed.

The behaviour of OpenSSL and of Node's own PKCS#12 reader is documented in the README with the version it was verified against. A correction there is a welcome issue, not a vulnerability report.

## Supported versions

Only the `main` branch and the latest tagged release receive fixes.
